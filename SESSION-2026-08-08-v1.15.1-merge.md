# Post-merge: startup runaway + lost cast session (same root cause)

Found on the first `pnpm dev` after the merge. **Not a v1.15.1 regression** — all of it lives
in fork hub code that had never been dev-run. Three reported symptoms, one chain:

1. Playback starts by itself on launch, while the bar reads "paused" and the pause button does
   nothing (only killing the app stops it).
2. It starts from the **first track** of the queue, not where the app was closed.
3. Relaunching the client while a Chromecast was playing **loses the session** — the still-playing
   speaker is treated as stopped.

## The chain

The cast bridge lives in Feishin's *own* main process, so relaunching the client kills it. The
hub relinquishes the active slot whenever the active device drops (`_disconnect`), so a restart
always lands in "session exists, no live receiver" — and then:

- **The renderer published over it.** The persisted queue rehydrates ~a moment after launch and
  fires `publishQueue` *before* `welcome` has arrived. The hub promotes any `setQueue` sender
  while the active slot is empty, so this stale copy became the session — at `index.current` and
  `positionMs.current`, both of which are fed by player *events* that never fired for a restored
  queue, i.e. **first track, position 0**. That is symptoms 2 and 3.
- **`adoptIfNoLiveReceiver` then loaded that session PLAYING.** `setQueue` hard-coded
  `status = PLAYING`, and the `mediaPause()` right after could land *before* the engine's async
  play did. Audio then ran under a store that already read PAUSED — and since the engines act on
  status *changes* only (`subscribePlayerStatus` fires when the value differs), every later
  pause, ours or the user's click, was a no-op. Symptom 1.
- **The bridge could never take the session back.** `maybeAdopt` required
  `session.activeDeviceId === this.hubDeviceId`, but the hub had just cleared that slot — so the
  one case the re-adoption path was written for (Feishin restarted, speaker still playing) was
  exactly the case it refused.

## Fixes

- `player.store.ts` — `setQueue` takes an optional `play` (default true), so a queue can be
  **loaded into PAUSED** rather than loaded-playing-then-paused. Removes the race at its source
  instead of chasing it with watchdogs.
- `use-hub.tsx` — `adoptIfNoLiveReceiver`, `do:load` (`play: false`) and `do:queueChanged`
  (a queue edit must not *start* playback either) all load with the correct state directly.
- `use-hub.tsx` — `publishQueue` returns early until `welcome` has been received
  (`myId.current === null`), and reads index/position from the live stores
  (`player.index`, the timestamp store) instead of the event-fed refs.
- `cast/index.ts` — `maybeAdopt` also fires on an **orphaned** session (`activeDeviceId == null`,
  non-empty queue). Adoption is only *claimed* if the device's running `contentId` matches a track
  in that session's queue, and the claim is an `act setQueue` carrying the session's own
  `savedQueueId` (a `report` from a non-active device is discarded by the hub, and reusing the id
  keeps the history record from forking).
- `use-hub.tsx` — the watchdogs keep the earlier `hardPause` + engine-clock `audioIsRolling()`
  detection as a net, now shared by all three call sites.

# Post-merge II: cast device idles out and never comes back

Re-adoption now works. The next failure is the *paused* case: leave playback paused on the
speaker for a couple of minutes and it goes away, while Feishin keeps insisting it's playing.
Unpausing makes no sound, resuming from the Google Home app is invisible to Feishin, and
switching away and back reconnects to nothing. Logs show `connect ETIMEDOUT <ip>:8009` and
`load failed Error: cast connect timeout`.

Three independent holes, all in `cast/index.ts`:

1. **A stale `castPlayer` outlives the receiver app.** A Chromecast tears the app down after a
   few idle minutes, but our player object survives — so `do:play` called `play()` into the void
   and reported playback that made no sound. Nothing noticed, because the only liveness check
   lived in the *ticker*, which returns early while paused.
2. **The bridge's address was frozen at first discovery.** `browser.on('up')` skipped any device
   with an existing bridge, so a DHCP move meant dialling the old address forever — which is
   exactly what `connect ETIMEDOUT` to a speaker that Google Home can still reach looks like.
3. **A failed load left the session claiming to play.** The retry's exception propagated to a
   caller that only logs, so `playing` stayed true and every client showed a running scrubber
   for a silent speaker.

## Fixes

- `castSessionAlive()` — `getStatus` with a 3 s timeout (a dead session answers nothing, so the
  timeout *is* the answer). `do:play` proves the session before using it and otherwise rebuilds
  from `lastPositionMs`. A false negative is harmless: reloading is the right recovery anyway.
- `onCastSocketClosed()` on the client's `close` event (added to the local `castv2-client.d.ts`
  shim) drops the stale session immediately, and re-joins if we were playing — which is also how
  a resume done from the Google Home app gets picked back up. `tearingDown` keeps our own
  `teardownCast()` from being mistaken for the device hanging up.
- `updateHost()` + `browser.on('up')` now refreshing an existing bridge; a failed connect calls
  `requeryCastDevices()` so the new address is asked for immediately, and the load retry waits
  1.2 s for that answer before dialling again.
- `loadCurrent` reports `isPlaying: false` when it gives up, so the UI stops lying.

`tsc` node: pass. `electron-vite build`: pass. eslint clean. **Not verified live** — needs a
paused speaker left to idle out, then unpause.
