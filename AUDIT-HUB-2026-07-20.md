# Hub Full Code Audit — Findings & Improvement Plan (2026-07-20)

## Context

Full audit of the navi-connect **hub** (`hub/hub.py`, ~650 LoC, stdlib + `websockets`): a
headless Spotify-Connect-style relay that owns the session *intent* (queue/order/repeat/shuffle/
active device) and routes commands to the active receiver. Audio never flows through it. This file
covers correctness, concurrency, robustness, efficiency, security, and feature ideas — **functionality
only**, no UI. Findings are verified by reading the code against `PROTOCOL.md`; nothing here has been
runtime-reproduced, and severities reflect that.

The related client-side hub bugs (Navic `RemoteSessionPlayer`/`HubManager`, Feishin `use-hub.tsx`)
are already tracked in the Navic/Feishin audits — this file is scoped to the Python hub itself.

---

## Area 1: Concurrency & connection lifecycle

### Bugs

| Sev | Location | Finding |
|---|---|---|
| **HIGH** | `_register` + `_disconnect` (`:325`, `:340`) | **Stale-socket clobber on reconnect.** Each `handler` keeps its own `ws` local; `_disconnect(dev)` unconditionally sets `dev.online=False`, `dev.ws=None`. On a reconnect blip the *new* connection registers (`dev.ws = new_ws`) **before** the old socket's `finally` fires — the old `_disconnect` then nulls the live new socket and marks the device offline. If that device was active, it also spuriously pauses + relinquishes active. This is a plausible contributor to the "remote randomly pauses / drops active" class of bugs. **Fix:** pass the socket to `_disconnect` and guard `if dev.ws is ws` before tearing down; ignore disconnects for a superseded socket. |
| **MED** | `_register` (`:325-338`) | **No eviction of the prior live socket.** A reconnect while the old WS is still half-open leaves *two* live sockets bound to one `Device`; both run `async for` and both emit `report`s, double-driving session state. **Fix:** on re-register, close the previous `dev.ws` (if any) before adopting the new one. |
| LOW | `handler` (`:290-300`) | First frame that is valid JSON but **not an object** (e.g. `"hi"` or `[]`) makes `msg.get(...)` raise `AttributeError`, which escapes the `(TimeoutError, JSONDecodeError)` catch → ungraceful close, noisy traceback. **Fix:** `if not isinstance(msg, dict): close(4002)`. |

### Notes

- Per-frame handling (`_on_message`) is correctly wrapped in `except Exception` so one bad frame
  can't kill the socket — good. Same non-dict issue exists there but is swallowed/logged, so it's
  benign.
- `asyncio.get_event_loop().create_future()` in `_transfer` (`:605`) works because a loop is running,
  but prefer `asyncio.get_running_loop()` (the former is deprecated when no loop is set).

## Area 2: Queue / order semantics

### Bugs

| Sev | Location | Finding |
|---|---|---|
| **MED** | `_rebuild_order` called from `enqueue`/`remove`/`move` (`:460`, `:512`, `:441`) | **Every queue edit re-randomizes the whole shuffle order.** `_rebuild_order` regenerates `order` from scratch (`[index] + random.shuffle(rest)`). So while shuffling, removing/moving/enqueuing a track throws away the user's entire upcoming shuffled order and reshuffles it. **Fix:** for edits (not `setQueue`/`shuffle`-toggle), patch `order` incrementally — drop/insert the affected index and renumber — instead of a full reshuffle. |
| **MED** | `_on_report` (`:389-390`) | **Position reports aren't guarded against a fresh `seek` intent.** `INTENT_GRACE` only protects `isPlaying`; an in-flight 1 Hz report carrying the *old* position lands right after a user `seek` and rewinds the scrubber. `seek` also never calls `_mark_play_intent`. This is a candidate source of the "progress bar blinks / jumps back" symptom. **Fix:** stamp a position-intent time on `seek`/`jump`/`next`/`previous` and reject contradicting position reports within the grace window. |
| LOW | `setQueue`/`jump`/`clear` (`:435-451`, `:549`) | `index` from the client isn't clamped to `len(queue)`. Downstream readers mostly guard (`_mirror_play_queue` bounds-checks, `getState` clamps client-side, `_step_index` falls back to 0 on `ValueError`), so this is latent, not live — but a malformed `index` still persists into `state.json`. **Fix:** `index = max(0, min(index, len(queue)-1))` on ingest. |

### Notes

- `_step_index` repeat/shuffle math is correct; `repeat=="one"` returning the same index for
  *previous* (restart track) is a defensible choice.
- `remove` of the current track correctly emits `jump` after `queueChanged` (well-commented). Good.

## Area 3: Navidrome savePlayQueue mirror

### Bugs / inefficiencies

| Sev | Location | Finding |
|---|---|---|
| **MED** | `_mirror_play_queue` (`:239-247`) | **Unthrottled, un-serialized mirror writes.** Every `changed` session broadcast (each play/pause/**seek**/index change) spawns a fresh `asyncio.create_task(to_thread(savePlayQueue))`. Rapid seeks/skips fire concurrent HTTP writes to Navidrome with **no ordering guarantee** — a slower earlier write can land last and persist a stale position. Tasks are also fire-and-forget (not tracked), risking "Task was destroyed but it is pending" churn. **Fix:** single-flight the mirror (one in-flight write; coalesce to the latest snapshot on completion) and debounce (e.g. 2–3 s), similar in spirit to `PROGRESS_THROTTLE`. |
| LOW | `_nd_auth_params` (`:117-120`) | Subsonic auth uses **MD5 token** with `v=1.16.1` — fine for Navidrome, but the salt is only 12 hex chars. Cosmetic; Navidrome accepts it. Worth a comment that this is Subsonic-mandated, not a security choice. |

### Notes

- The mirror is correctly best-effort and fully optional (guarded by `MIRROR_PLAYQUEUE` + creds);
  failures are logged and swallowed. Good separation.

## Area 4: Persistence & I/O

| Sev | Location | Finding |
|---|---|---|
| LOW | `_save` (`:190-206`) | **Synchronous disk write on the event-loop thread**, called on every `_register` and every `_broadcast_session`. For a personal-scale JSON file this is negligible, but it does block the loop briefly under rapid edits. The atomic `tmp`+`os.replace` pattern is correct. **Optional:** offload to `to_thread`, or debounce saves. |
| LOW | `main` / shutdown (`:647-651`) | Only `KeyboardInterrupt` is handled; a container `docker stop` sends **SIGTERM**, which isn't trapped for a final flush. Mitigated because state is saved on every change, so at most the last few `position_ms` are lost. **Optional:** trap SIGTERM → `_save()`. |
| LOW | `_load` (`:177-183`) | Device registry is loaded but **never pruned** — devices persist forever. Over time `state.json` accumulates dead devices that still appear in `devices` broadcasts. **Fix/feature:** drop devices not seen in N days on load (see Area 6). |

## Area 5: Security & operability

| Sev | Location | Finding |
|---|---|---|
| **MED** | `handler` (`:292`) | **Non-constant-time token compare** (`msg.get("token") != TOKEN`). On a LAN the risk is low, but it's a one-line hardening: `hmac.compare_digest(got, TOKEN)`. |
| LOW | transport (`main`, `:641`) | **`ws://` only, no TLS.** Acceptable on a trusted LAN; if the hub is ever port-forwarded the shared token travels in cleartext. Document "put it behind a `wss` reverse proxy if exposed." |
| LOW | `_on_act` DIAG logs (`:426`, `:399`, `:229`) | **Temporary diagnostic logging is still live** (the "pause-echo hunt" `ACT`/`REPORT`/`SESSION` lines). Very chatty at 1 Hz and prints device names. **Fix:** gate behind a `HUB_DEBUG` env flag (default off) or remove once the unpause bug is closed. |
| LOW | `Dockerfile` | **No `HEALTHCHECK`** and the hub exposes no health endpoint, so `restart: unless-stopped` can't detect a wedged-but-alive process. See Area 6 (health endpoint). |
| LOW | `main` (`:643`) | `max_size=4 MiB` caps a frame; a very large queue with rich metadata could approach it. Low risk, but a `setQueue` over the cap closes the socket with no friendly error. **Optional:** cap queue length server-side with an `error` reply. |

## Area 6: Feature ideas (new capability)

Ordered roughly by value-to-effort for a personal setup.

| Effort | Feature | Sketch |
|---|---|---|
| **S** | **`HUB_DEBUG` flag** | Gate all DIAG logging; keep normal logs terse. Trivial, unblocks leaving instrumentation in the tree. |
| **S** | **Health endpoint / healthcheck** | Tiny `aiohttp`-free path: run a second `asyncio` server on `HUB_PORT+1` returning `200 {devices, active, rev}`, or accept an HTTP `GET /healthz` upgrade-less request on the same port. Wire `HEALTHCHECK` in the Dockerfile. |
| **S** | **Device auto-prune** | On `_load` (and periodically), drop devices with `lastSeen` older than `HUB_DEVICE_TTL_DAYS` (default 30). Keeps the picker clean. |
| **S** | **Sleep timer** | New `act` `sleep {afterMs}`; hub schedules a task that issues `pause` to the active receiver and clears intent. Purely hub-side, no client changes beyond a button. |
| **M** | **ListenBrainz scrobbling** | You already run `lb-bot`. The hub sees every track change + play threshold — it's the natural scrobble point. On `index` advance past ~50%/4 min, POST `submit-listens`. Reuses existing LB token; makes remote playback scrobble regardless of which client is active. |
| **M** | **Recently-played / history** | Ring buffer of the last N played track ids (+ timestamps) persisted in `state.json`; expose via `welcome`/a `history` frame. Feeds a "recently played" view and future queue-undo parity with the client. |
| **M** | **Server-authoritative favorite/rating** | `favorite`/`rating` currently just forward to the active receiver, so only that device's Navidrome call happens and other controllers' UIs go stale. Have the hub call Navidrome `star/setRating` directly (reusing the mirror's auth) and broadcast the change so every controller updates. |
| **M** | **Graceful takeover / "who's controlling"** | Broadcast the id of the last controller that mutated intent, so UIs can show "Playing from Bedroom, controlled by Phone." Cheap given the hub already sees every `act`. |
| **L** | **Multi-zone / rooms** | Protocol is single global session by design. A `roomId` dimension (map of independent `Session`s + device→room binding) would enable true multi-room without audio sync. Large surface change; only worth it if you actually want independent zones. |

## Suggested fix order

1. **HIGH — stale-socket clobber** (`_disconnect` ws-guard + evict old socket on re-register). Most
   likely to be silently corrupting active-device/pause state and is a small, well-contained fix.
2. **MED — seek/position intent grace** (stop reports rewinding the scrubber). Directly targets the
   still-open "progress bar blinks / unpause" symptom you've been chasing.
3. **MED — shuffle order preservation** on queue edits.
4. **MED — mirror single-flight + debounce.**
5. **MED — `hmac.compare_digest` token check.**
6. **S cleanups — `HUB_DEBUG` gate for DIAG logs, index clamping, non-dict first-frame guard.**
7. Then pick from Area 6 features (health endpoint + auto-prune are the cheapest wins;
   ListenBrainz scrobbling is the highest-value given `lb-bot` already exists).

All of the above are Python-only — no APK build required — so each is independently testable against
`tools/fake_receiver.py` + `tools/controller.py` (and `tools/test_transfer.py` should be extended to
cover the reconnect-clobber and shuffle-edit cases).
